## 1. 模块职责

M2 接收 M1 输出的 `parsed`（结构化简历）和 `req`（结构化岗位要求），调用 LLM 评估匹配度，返回 0–100 整数分数及恰好三条关键差距。M2 与 M3 都依赖 M1，但彼此独立；由前端在 M1 完成后并行调用。

## 2. 文件位置

| 文件 | 职责 |
|------|------|
| `backend/app/contracts/match.py` | 请求、响应、LLM 输出的数据契约与校验 |
| `backend/app/prompts/match.md` | 评分标准和 JSON 输出要求 |
| `backend/app/services/match_service.py` | 组装输入并调用统一 LLM 客户端 |
| `backend/app/routers/match.py` | `POST /api/match` 接口 |
| `backend/scripts/try_match.py` | 使用 M1 样例调用运行中的服务 |
| `backend/tests/test_*_match.py`、`test_match_*.py` | 契约、服务、接口、真实 LLM 集成测试 |
| `backend/fixtures/parsed.json`、`match.json` | 输入与输出样例 |

## 3. 接口：POST /api/match

请求体直接使用 M1 的 `POST /api/parse` 响应：

```json
{
  "parsed": {"raw_text": "简历原文", "skills": ["Python"], "experiences": [], "education": [], "metrics": []},
  "req": {"hard_skills": ["Python"], "responsibilities": ["开发接口"], "keywords": [], "min_years": 0}
}
```

`parsed` 和 `req` 必填。`parsed` 至少要有原文、技能、经历或量化成果之一；`req` 至少要有硬技能、职责或关键词之一。缺字段或缺有效内容返回 400。

响应体字段：

| 字段 | 类型 | 规则 |
|------|------|------|
| `score` | int | 0–100 的综合匹配分 |
| `gaps` | Gap[3] | 恰好三条，按重要性排序 |
| `gaps[].jd` | string | 对应的岗位要求 |
| `gaps[].resume` | string | 简历证据或“未体现” |
| `gaps[].detail` | string | 差距解释与修改方向 |
| `dimensions` | object，可选 | `hard_skill`、`project`、`metric`、`domain` |

响应格式见 `backend/fixtures/match.json`。

错误格式统一为 `{"code": "...", "message": "..."}`：

| HTTP | code | 条件 |
|------|------|------|
| 400 | `INVALID_INPUT` | 请求体缺字段或没有有效简历/JD 内容 |
| 422 | `LLM_OUTPUT_INVALID` | 模型输出非 JSON、分数越界或差距数量错误，重试后仍失败 |
| 500 | `LLM_UPSTREAM_ERROR` | 模型服务网络错误或超时 |

## 4. 评分规则

| 维度 | 权重 | 观察依据 |
|------|----------|----------|
| `hard_skill` | 40% | JD 硬性技能在简历中明确体现的覆盖度 |
| `project` | 30% | 项目/工作场景、职责和技术栈与岗位的相关性 |
| `metric` | 20% | 数字、基线、结果等量化成果的充分度 |
| `domain` | 10% | 行业背景、工具和岗位关键词的实际使用证据 |

`score` 是结合上述权重得到的综合分。设计文档只规定权重，没有规定 `dimensions` 各项的得分上限，也没有要求四项相加等于 `score`。`dimensions` 为可选字段；若模型省略，仍可接受合法的 `score` 与三条 `gaps`。

## 5. 内部流程

```text
M1 的 parsed + req
  → （路由层）MatchRequest 校验
  → JSON 序列化并拼入 user 消息
  → prompts/match.md 作为 system 消息
  → core/llm.py 调用模型并按 MatchResult 校验
  → MatchResponse 返回给前端
```

`core/llm.py` 负责超时、格式错误时重试一次、JSON 提取与异常转换。M2 服务不写数据库；前端拿到 M2 和 M3 结果后，再调用 `/api/report` 落库。

## 6. 单独使用

在项目根目录配置 `.env`，安装依赖后启动服务：

```bash
cd backend
python -m uvicorn app.main:app --reload
```

另开终端，在项目根目录运行：

```bash
python backend/scripts/try_match.py
```

也可在 `http://127.0.0.1:8000/docs` 打开 `POST /api/match`，粘贴 `backend/fixtures/parsed.json` 的内容执行。

## 7. 测试

在项目根目录运行：

```bash
pytest backend/tests/test_contracts_match.py backend/tests/test_match_service.py backend/tests/test_match_router.py
```

```bash
pytest backend/tests/test_match_integration.py -v -s
```

集成测试需要真实 `.env` 配置；占位密钥会自动跳过。测试配置沿用 M1 的 `backend/tests/conftest.py`，项目根目录须存在 `.env` 文件。
