## 1. 背景与目的

### 1.1 背景

求职者在投递前普遍缺少客观、可落地的简历反馈：自评容易陷入“写得不错”的盲区，而人工修改成本高、反馈慢。常见的痛点是：

- 简历与目标岗位匹配度不清，不知道差距在哪；
- 空话、缺少量化、时间线矛盾等硬伤难以自查；
- 面试前缺少针对性的追问练习，无法检验自己能否把经历讲清楚。

因此需要一个工具：输入简历和目标岗位 JD，自动给出匹配分与差距、标红风险点、生成致命追问并支持逐题点评，以及最差经历的 STAR 改写参考。

### 1.2 目标

- 一次提交（简历 + JD），自动产出结构化诊断报告：匹配分、3 条差距、风险标红、最多 5 条追问。
- 提供两项后续动作：逐题问答点评（模拟面试）与最差经历的 STAR 重写。
- 诊断链路（解析 → 并行匹配/拷问 → 落库）稳定可复现，失败可重试、不留半成品。
- 全量接口与数据契约清晰，便于团队分工联调与测试追溯。

### 1.3 非目标

- 不做登录、用户体系、多租户与权限分级。
- 不做简历文件上传与解析（PDF / Word），仅支持纯文本粘贴。
- 不做追问跳题、回头修改已答答案、根据回答动态生成新追问。
- 不做前端刷新后未提交输入的恢复。

### 1.4 项目概述

基于多 Agent 协作的**简历诊断与模拟面试系统**：求职者粘贴简历文本与目标岗位 JD，系统经「解析 → 匹配打分 + 风险拷问（并行）→ 落库 → STAR 重写 / 逐题问答」四段式流程，输出一页诊断报告。

- 技术栈：Python 3.13 + FastAPI + Streamlit + SQLite + SQLAlchemy + OpenAI 兼容 LLM 接口。
- 输入/输出：两段纯文本（简历 + JD）进，一页结构化诊断报告出。
- 系统形态：前后端分离（Streamlit 前端 + FastAPI 后端），本机 HTTP 交换 JSON。

## 3. 用户角色与使用场景

### 3.1 用户角色

| 角色 | 描述 | 主要诉求 |
|---|---|---|
| 求职者 | 准备投递或面试的候选人 | 快速看清简历与岗位的匹配度与差距、发现简历风险点、针对性练习面试追问、获得经历改写参考 |

> 本系统为课程项目，单用户、无登录、无权限分级。

### 3.2 典型场景

- **场景 1**：求职者在投递某岗位前，粘贴自己的简历和该岗位 JD，需要得到匹配分与差距，以便针对性修改简历。
- **场景 2**：求职者拿到诊断报告后，想针对被标红的致命风险点练习面试追问，检验自己能否把这段经历讲清楚。
- **场景 3**：求职者觉得某段经历写得最弱，点击 STAR 重写，得到改前/改后对比与复评分，作为修改参考。

## 4. 功能需求

> 编号规则：FR-xxx，与设计文档 02 的模块 M1–M4 对应。优先级：P0 = Must（一期核心，缺了系统不可用）；P1 = Should（诊断后的增值动作，条件允许先做）。

| 编号 | 需求描述 | 优先级 | 验收标准 |
|---|---|---|---|
| FR-001 | 系统支持粘贴简历与 JD 文本并做输入校验 | P0 | 简历 strip 后 100–8000 字、JD 50–8000 字，超出截断；为空/过短时前端就地提示且**不发起后端请求**；点击「开始诊断」后自动走完「解析 → 并行匹配/拷问 → 落库 → 展示」 |
| FR-002 | 系统解析简历与 JD 为结构化 JSON（M1） | P0 | 输出 `parsed`(ResumeParsed) 与 `req`(JDReq)，符合 contracts；`parsed.raw_text` 与请求 `resume_text` 完全一致；LLM 输出非法返 422、超时/网络返 500 |
| FR-003 | 系统按目标岗位打分并给出 3 条差距（M2） | P0 | `score` 为 0–100 整数（越界 422）；`gaps` 恰好 3 条（不足/超出 422）；`dimensions` 可选；入参不完整 400 |
| FR-004 | 系统找出风险片段并生成最多 5 条致命追问（M3） | P0 | `risks` 覆盖空话/无数字/逻辑矛盾三类，含类型·片段·原因·偏移；`questions` 数量 `N=min(5,致命风险数)`、每条带有效 `risk_index`、按致命度排序、无致命风险时为空数组、不生成无关题；`weakest_experience_id` 存在于 `parsed.experiences`；超 5 条/越界/id 不存在 422、缺 `raw_text` 400 |
| FR-005 | 系统一次事务落库三张表（M4） | P0 | `POST /api/report` 一次事务写 `resume`/`jd`/`report` 并返回三个 id；任一步失败整体回滚不留半成品；`score` CHECK 0–100；嵌套模型不合法 400、DB 异常 500 |
| FR-006 | 系统对最差/指定经历做 STAR 重写（M4） | P1 | 目标经历=`experience_id` 否则 `weakest_experience_id`；输出 `before`/`after`/`star`(S/T/A/R)（缺失 422）；`improved_score` ≤ 原分时钳制为 `score+5`（上限 100）保证大于原分；更新 `report.rewrite`；经历不存在 400、报告不存在 404、LLM 异常 500 |
| FR-007 | 系统对回答给出规则点评（M4） | P1 | 一次一题（`report_id+question_index+answer`）；后端按 `question_index` 取原题、不信任前端文本；规则点评；追加 `report.qa`；同题重复按覆盖；`answer` 1–1000 字、越界或为空 400、报告不存在 404 |
| FR-008 | 系统支持按 report_id 回显完整报告（M4） | P0 | `GET /api/report/{id}` 联查三表、反序列化 JSON 字段、返回前端可渲染结构；`report_id` 不存在 404；刷新页面能恢复本次报告 |
| FR-009 | 系统提供 Streamlit 单页展示与交互 | P0 | 展示匹配分、3 条差距、风险标红、追问、STAR 改前/改后与复评分、问答点评；追问一次一题、答完显示点评再下一题、末题答完展示全部；`n=0` 显示「未发现致命问题」；首版不支持跳题与回头改答案 |

### 4.1 需求详情

#### FR-001 简历与 JD 输入校验

- **描述**：用户粘贴简历纯文本和目标岗位 JD 纯文本，系统做长度校验并触发诊断流程。
- **输入 / 触发条件**：用户在页面输入 `resume_text`、`jd_text`，点击「开始诊断」。
- **处理规则**：strip 后简历 100–8000 字、JD 50–8000 字，超出截断；为空或过短就地提示、不发起后端请求。
- **输出 / 结果**：截断后的 `resume_text`、`jd_text`，作为解析（FR-002）的输入。
- **异常与边界**：为空/过短 → 语义 400，前端输入框下方提示、不请求。
- **验收标准**：
  - Given 简历 strip 后 80 字，When 点击「开始诊断」，Then 前端提示过短且不发起请求。
  - Given 简历 9000 字，When 校验，Then 截断到 8000 字后继续。
  - Given 输入合法，When 点击「开始诊断」，Then 自动按序走完「解析 → 并行匹配/拷问 → 落库 → 展示」。

#### FR-002 简历解析（M1）

- **描述**：把简历与 JD 两段纯文本转成结构化 JSON，是链路的起点。
- **输入 / 触发条件**：截断后的 `resume_text`、`jd_text`，输入校验通过后自动触发。
- **处理规则**：调 LLM #1，Prompt 拼入简历与 JD；输出经 JSON 提取 + Pydantic 校验。
- **输出 / 结果**：`parsed`（ResumeParsed，`raw_text` = 请求 `resume_text`）、`req`（JDReq）。
- **异常与边界**：LLM 输出非 JSON / 字段缺失 → 422；超时或网络异常 → 500。
- **验收标准**：
  - Given 合法文本，When 调 `POST /api/parse`，Then 返回 `parsed` 与 `req`，且 `parsed.raw_text == resume_text`。
  - Given LLM 返回非法 JSON，When 解析，Then 返回 422。

#### FR-003 匹配打分（M2）

- **描述**：按目标岗位给简历打分，并给出恰好 3 条关键差距。
- **输入 / 触发条件**：`parsed`、`req`，解析完成后与拷问（FR-004）并行触发。
- **处理规则**：四维度加权——硬性技能覆盖度 40%、项目经历相关性 30%、量化成果充分度 20%、行业/工具匹配 10%。
- **输出 / 结果**：`score`（0–100 整数）、`gaps`（恰好 3 条）、`dimensions`（可选，各维度得分）。
- **异常与边界**：`score` 越界 → 422；`gaps` 非 3 条 → 422；入参不完整 → 400。
- **验收标准**：
  - Given `parsed` + `req` 完整，When 调 `POST /api/match`，Then `score` 为 0–100 整数且 `gaps` 恰好 3 条。
  - Given 返回分数 120，When 校验，Then 返回 422。

#### FR-004 风险拷问

- **描述**：找出简历中的风险片段并标红，生成最多 5 条致命追问。
- **输入 / 触发条件**：`parsed`（含 `raw_text` 与 `experiences[].raw`）、`req`；在解析完成后与匹配并行触发。
- **处理规则**：
  | 类型 | 判定 |
  |------|------|
  | 空话 | 命中词典：认真负责、沟通能力强、团队协作、学习能力强、抗压、责任心强、一致好评 |
  | 无数字 | 分句含「大幅/显著/明显/极大/全面提升/有效」，且句内无数字、百分比、倍数、QPS、ms |
  | 逻辑矛盾 | 日期起止倒置、结束时间晚于当前、教育结束早于工作开始 |
  - 先有风险、再有追问：每条追问带 `risk_index` 指向 `risks` 中的一条。
  - 数量 `N = min(5, 致命风险数)`；按致命度排序：逻辑矛盾 > 无数字 > 空话，与 JD 直接相关的缺口优先。
  - 无致命风险时 `questions` 为空数组；不生成与简历无关的通用题。
- **输出 / 结果**：`risks`、`questions`（0–5 条）、`weakest_experience_id`。
- **异常与边界**：问题超 5 条 / `risk_index` 越界 / id 不存在 → 422；缺 `raw_text` → 400；LLM 超时或网络异常 → 500。
- **验收标准**：
  - Given 简历含「大幅提升了系统性能」且无数字，When 执行拷问，Then 命中「无数字」风险并出现在 `risks`。
  - Given 简历存在日期倒置（如 2024.09–2024.06），When 执行拷问，Then 命中「逻辑矛盾」且排序最靠前。
  - Given 简历无任何致命风险，When 执行拷问，Then `questions` 为空数组。

#### FR-005 报告汇总落库

- **描述**：匹配与拷问两段结果都返回后，一次事务写入三张表。
- **输入 / 触发条件**：`resume_text`、`jd_text`、`parsed`、`req`、`score`、`gaps`、`risks`、`questions`、`weakest_experience_id`；匹配与拷问均返回后触发。
- **处理规则**：一个事务内依次插入 `resume`、`jd`、`report`，提交后返回三个 id；任一步失败整体回滚。
- **输出 / 结果**：`report_id`、`resume_id`、`jd_id`。
- **异常与边界**：嵌套模型不合法 → 400；数据库异常 → 500（回滚）。
- **验收标准**：
  - Given 匹配与拷问均成功，When 调 `POST /api/report`，Then 三表各新增一条且返回三个 id。
  - Given 落库过程中某表写入失败，When 事务回滚，Then 三表均无新增（无半成品）。

#### FR-006 STAR 重写

- **描述**：对最差（或指定）经历做 STAR 重写，输出改前/改后对比。
- **输入 / 触发条件**：`report_id` + 可选 `experience_id`；用户点击按钮触发。
- **处理规则**：
  1. 按 `report_id` 取 `parsed`、`req`、`risks`、原 `score`。
  2. 目标经历 = 请求 `experience_id`，否则用报告里的 `weakest_experience_id`。
  3. 用目标经历原文、风险、JD 关键词拼 Prompt 调 LLM。
  4. 校验 `before`/`after`/`star` 四要素；`improved_score` 若 ≤ 原分，钳制为 `score + 5`（上限 100）。
  5. 更新 `report.rewrite`，返回对比结果。
- **输出 / 结果**：`before`、`after`、`star`（S/T/A/R）、`improved_score`。
- **异常与边界**：经历 id 不存在 → 400；报告不存在 → 404；STAR 字段缺失 → 422；LLM 异常 → 500。
- **验收标准**：
  - Given 报告存在且未指定 `experience_id`，When 调 `POST /api/rewrite`，Then 目标经历为 `weakest_experience_id` 对应经历。
  - Given 重写后复评分 ≤ 原分，When 校验复评分，Then 钳制为 `score + 5` 且不超过 100。

#### FR-007 逐题问答点评（M4）

- **描述**：用户逐题作答，系统给出规则点评（不调 LLM）。
- **输入 / 触发条件**：`report_id + question_index + answer`，诊断落库后用户逐题提交。
- **处理规则**：按 `question_index` 从报告取原题（不信任前端文本）；规则点评——没数字 → 缺量化、少于 30 字 → 缺细节、含「大概/可能/应该」→ 缺具体事实；追加 `report.qa`（题号/问题/回答/点评），同题重复按覆盖。
- **输出 / 结果**：`comment`（一句点评）。
- **异常与边界**：`answer` 1–1000 字；越界或为空 → 400；报告不存在 → 404；DB 更新失败 → 500。
- **验收标准**：
  - Given 用户提交「大概吧」这类回答，When 点评，Then 返回含「缺具体事实」的点评。
  - Given 同题第二次提交，When 写入，Then 覆盖首次记录而非追加两条。

#### FR-008 报告回显与刷新恢复（M4）

- **描述**：按 `report_id` 回显完整报告。
- **输入 / 触发条件**：`report_id`，页面加载/刷新时触发。
- **处理规则**：联查 `resume`/`jd`/`report` 三表，反序列化 JSON 字段，组装前端可渲染结构。
- **输出 / 结果**：`resume_text`、`parsed`、`jd_text`、`req`、`score`、`gaps`、`risks`、`questions`、`weakest_experience_id`、`qa`、`rewrite`、`created_at`。
- **异常与边界**：`report_id` 不存在 → 404。
- **验收标准**：
  - Given 已落库的 `report_id`，When 调 `GET /api/report/{id}`，Then 返回含全部字段的聚合报告。
  - Given 不存在的 id，When 调 `GET /api/report/{id}`，Then 返回 404。

#### FR-009 前端展示

- **描述**：Streamlit 单页展示诊断报告并承载交互。
- **输入 / 触发条件**：报告数据（来自回显接口）与用户操作。
- **处理规则**：展示匹配分、3 条差距、风险标红、追问、STAR 改前/改后与复评分、问答点评；追问一次一题、提交后显示点评再进入下一题、末题答完展示全部问答；`n=0` 显示「未发现致命问题」。
- **输出 / 结果**：可交互单页界面。
- **异常与边界**：首版不支持跳题、回头改答案；未提交输入刷新丢失（接受）。
- **验收标准**：
  - Given 诊断完成，When 渲染页面，Then 展示匹配分、3 条差距、标红、追问、STAR 与问答区域。
  - Given `questions` 为空，When 渲染追问区，Then 显示「未发现致命问题」。

## 5. 非功能需求

| 编号 | 类别 | 需求描述 | 验收方式 |
|---|---|---|---|
| NFR-001 | 错误处理 | 统一错误码与 HTTP 状态：`INVALID_INPUT`=400、`NOT_FOUND`=404、`LLM_OUTPUT_INVALID`=422、`LLM_UPSTREAM_ERROR`=500、`DB_ERROR`=500、`INTERNAL_ERROR`=500，响应体 `{code, message}` | 接口测试覆盖各类错误场景 |
| NFR-002 | 性能/超时 | 接口超时：parse/match/interrogate/rewrite 30s；report 5s；GET report 5s；qa 5s（见 02-设计文档 5.1 接口总览） | 接口测试 / 联调观察 |
| NFR-003 | 可靠性 | 统一 LLM 客户端：统一超时、失败重试一次、JSON 提取、错误抛出 | 单元测试 + 异常注入 |
| NFR-004 | 失败语义 | 诊断链路（解析/匹配/拷问/落库）任一步失败即终止本次诊断；问答/重写失败只影响当前动作、重试即可 | 接口测试 |
| NFR-005 | 可维护性 | 分层清晰（routers / services / core / contracts），SQL 唯一入口在 `core/db.py`，业务不直接碰数据库 | 代码评审 |
| NFR-006 | 数据持久化 | SQLite 单机持久化，`backend/data/` 运行时生成、不提交 Git | 检查 .gitignore / 仓库提交内容 |

## 6. 外部接口与依赖

| 依赖项 | 类型 | 说明 |
|---|---|---|
| LLM 服务（OpenAI 兼容接口） | 外部 | 用于解析/匹配/拷问/重写共 4 次生成调用；BASE_URL、MODEL、API_KEY 由 `.env` 配置，单次调用超时 30s |
| 前端 ↔ 后端 HTTP | 内部 | Streamlit 通过 httpx 调 FastAPI 的 7 个接口，本机 HTTP 交换 JSON |
| SQLite 数据库 | 内部 | 三张表（resume / jd / report）持久化 |
| pytest 测试框架 | 内部 | 单元测试与接口测试 |

## 7. 约束与假设

- **约束**：
  - 技术栈固定：Python 3.13 + FastAPI + Uvicorn + Streamlit + SQLite + SQLAlchemy 2 + Pydantic v2 + httpx + pytest。
  - 课程项目，无登录/多租户/权限分级，单机单用户运行。
  - LLM 一律通过 OpenAI 兼容 HTTP 接口接入，便于换模型。
  - `backend/data/` 与 `.env` 不提交 Git。
- **假设**：
  - 用户以纯文本粘贴简历与 JD（不传文件）。
  - 运行时存在可用的 LLM API Key 与网络。
  - LLM 输出基本符合契约，异常情况由校验与重试兜底。
