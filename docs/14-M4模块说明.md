## 1. 这个模块是干什么的

一句话：**M1/M2/M3 把简历「读懂」之后，M4 负责把结果存下来、读出来，并承载诊断之后的两件增值动作（逐题问答、STAR 重写），最后用 Streamlit 把整条链路串成一个可操作的单页。**

```text
parse ──► （match ∥ interrogate） ──► POST /api/report ──► report_id
                                              │
                        ┌─────────────────────┴─────────────────────┐
                        ▼                                           ▼
                 POST /api/qa（逐题）                       POST /api/rewrite
                        └──────────────► GET /api/report/{id} ◄─────┘
                                          （刷新回显）
```

必须记住的一条：**`report_id` 只由 `POST /api/report` 产生。**
`/api/match`、`/api/interrogate` 都不落库、不返回 `report_id`，前端不能从它们身上“猜”。

## 3. 四个接口

### 3.1 `POST /api/report`（P0，唯一 report_id 来源）

**请求**（§5.5）：`resume_text`、`jd_text`、`parsed`、`req`、`score`、`gaps`（恰好 3 条）、`risks`、`questions`、`weakest_experience_id`。

**响应**：`{report_id, resume_id, jd_id}`。

**事务**：一个 `get_session()` 内依次写 `resume`、`jd`、`report`；任何一步失败 `DBError` → 500 `DB_ERROR`，整体回滚。

**校验**：
- `score` 越界 400、`gaps` 不是 3 条 400、`weakest_experience_id` 不在 `parsed.experiences` 里 400（全部 `INVALID_INPUT`）；
- **输入填反校验**：简历框里出现「岗位职责/任职要求/招聘」等 JD 特征（≥2 个），且 JD 框里出现履历、日期区间、邮箱或电话 → 400 `INVALID_INPUT`，提示交换两个输入框；
- **「同一人」校验**：落库前调用 `report_guard.detect_resume_anomalies()`，命中以下任一条即 400 `INVALID_INPUT`，并提示具体原因——
  - 文本里出现多个姓名（首行姓名 / `姓名：X`）；
  - 全职工作与实习时间区间重叠；
  - 在校时间与全职工作重叠；
  - 自称「应届」但有 2 年以上的全职经历。
  这样两个人拼在一起的简历不会被打分、存档，也不会生成看似正常的报告；
- 不新增数据库列：M3 的 `risks / questions / weakest_experience_id` 按设计文档 6.2 合并成一个 JSON 对象存进 `report.risks`，`core/` 和 `models.py` 一行都不用改。

### 3.2 `GET /api/report/{report_id}`（P0，刷新回显）

联查 `resume`/`jd`/`report`，反序列化 `parsed_json`、`req_json`、`gaps`、`risks`、`questions`、`qa`、`rewrite`，返回 §5.6 全字段：

`report_id`、`resume_text`、`parsed`、`jd_text`、`req`、`score`、`gaps`、`risks`、`questions`、`weakest_experience_id`、`qa`、`rewrite`、`created_at`。

注意主键字段名是 **`report_id`**，不再叫 `id`；`created_at` 是 `YYYY-MM-DD HH:MM:SS` 字符串。不存在 → 404 `NOT_FOUND`。

### 3.3 `POST /api/qa`（P1，LLM 逐题点评）

**请求**：`{report_id, question_index, answer}`。**前端不传问题文本**，后端按 `question_index` 从报告里取原题。

- `answer` 1–1000 字，空串/全空白/超长 → 400 `INVALID_INPUT`；
- `question_index` 越界 → 400 `INVALID_INPUT`；
- 报告不存在 → 404 `NOT_FOUND`（以前是 200 + 字符串「未找到报告」，已修正）；
- 同一题重复提交按 `question_index` **覆盖**，不追加第二条；
- 响应 `{comment}`，`report.qa` 每条含 `question_index/question/answer/comment`。

点评由 LLM 生成（设计文档 v1.1）：Prompt 输入原题、用户回答、该题对应的风险（按 `risk_index` 取）和 JD 关键词，要求给出一句具体、可执行的改进建议，不重复题目、不编造事实。

- **接口超时 30s**（设计文档 §5.1，v1.1 由 5s 调整）：LLM 调用统一走 `core/llm.py`，读 `settings.llm_timeout`（默认 30，`.env` 未覆盖）；
- `comment` 为空/全空白或不合契约 → 422 `LLM_OUTPUT_INVALID`；
- 模型超时/网络异常 → 500 `LLM_UPSTREAM_ERROR`。

实测输出示例（DeepSeek）：回答跑题时返回「点评：回答完全答非所问，未回应时间倒置问题。应直接说明真实起止……」，点评内容会随题目和回答变化。

### 3.4 `POST /api/rewrite`（P1，真 LLM）

**请求**：`{report_id, experience_id?}`。不传 `experience_id` 时用报告落库时存的 `weakest_experience_id`，**不再写死 `proj_1`**。

- `before` 一律取自简历里目标经历的原文，模型只负责 `after/star/improved_score`；
- 目标经历不存在或没有原文 → 400 `INVALID_INPUT`；报告不存在 → 404；
- 模型缺 S/T/A/R → 422 `LLM_OUTPUT_INVALID`；网络异常 → 500 `LLM_UPSTREAM_ERROR`；
- `improved_score` 若 ≤ 原分，钳制为 `score + 5`，上限 100；原分已 100 时保持 100；
- 成功回写 `report.rewrite` 并返回 `{before, after, star, improved_score}`。

## 4. 数据库（不改表结构）

只用 C 已经建好的三张表，没有新增列、没有迁移脚本：

| 表.字段 | 存什么 |
|---------|--------|
| `resume.raw_text` / `resume.parsed_json` | 简历原文 / M1 的 `parsed` |
| `jd.raw_text` / `jd.req_json` | JD 原文 / M1 的 `req` |
| `report.gaps` | M2 的三条差距（JSON 数组） |
| `report.risks` | M3 的三段结果合成一个 JSON 对象：`{"risks": [...], "questions": [...], "weakest_experience_id": "proj_1"}` |
| `report.qa` | 问答记录数组，按 `question_index` 覆盖 |
| `report.rewrite` | 重写结果 |

`report_service.load_interrogate()` 负责拆这个对象；如果遇到早期只存了 `risks` 数组的行，会按 `questions=[]`、`weakest_experience_id=None` 兼容读取，不会 500。

> 这样设计是因为 `report` 表的字段属于 C 的 `core/models.py`，M4 不改平台骨架；设计文档 6.2 本来也要求把 `risks/questions/weakest_experience_id` 一起放进 `report.risks`。前端拿到的 `GET` 响应依然是拆开的三个字段，不受存储格式影响。

## 5. 前端（Streamlit）

`frontend/streamlit_app.py` 单页，实际交互：

1. 本地校验：简历 strip 后 ≥100 字、JD ≥50 字，超长截断到 8000；不够就就地提示、**不发请求**。若检测到「简历/JD 填反」或「多个姓名」，也直接提示、不发起诊断。
2. `POST /api/parse`。
3. `ThreadPoolExecutor` 并发 `POST /api/match` 与 `POST /api/interrogate`，任一失败即终止本次诊断。
4. 两段都成功后 `POST /api/report`，拿 `report_id`，把 `?report_id=` 写进 URL，再 `GET` 一次渲染。
5. 右栏追问一次只显示一题：提交后显示点评并自动进入下一题；全部答完显示「全部题目已答完」；`questions=[]` 显示「未发现致命问题 ✅」。
6. STAR 重写按钮：调 `/api/rewrite`，展示改前原文 + 改后文本 + 复评分。
7. 刷新页面：从 URL 的 `report_id` 调 `GET /api/report/{id}` 恢复；404 时清掉参数、回到输入态。

错误提示按 §7.5：422 →「生成失败，请重试」，500 →「服务超时 / 保存失败，请重试」，404 →「报告不存在，请重新诊断」。

## 7. 常见坑

| 现象 | 原因 / 处理 |
|------|-------------|
| 前端点「开始诊断」提示未返回 `report_id` | 旧版从 `/api/match` 取 id。现在只认 `POST /api/report` 的响应 |
| `GET /api/report/1` 返回 404 | 库里没有该 id；先走一次完整诊断落库，或检查是否用了别的数据库文件 |
| `GET` 返回的 `questions` 为空但前端显示过追问 | 早期行只在 `report.risks` 存了数组；重新走一次诊断落库即可，新数据是 `{risks, questions, weakest_experience_id}` |
| `POST /api/qa` 返回 400「question_index 越界」 | 报告里没有追问（`questions=[]`），或前端题号与报告不一致 |
| 重写返回 400「经历不存在」 | `experience_id` 不在 `parsed.experiences` 里；不传时用 `weakest_experience_id` |
| 重写 `improved_score` 总比模型给的高 | 钳制规则：低于 `score+5` 时抬到 `score+5`，这是契约要求 |
| `POST /api/report` 返回 400「简历信息可能不属于同一个人」 | 输入里混了两份简历（多个姓名 / 全职与实习重叠 / 在校与全职重叠 / 应届与多年经验冲突）；拆成单份再提交 |
| `POST /api/report` 返回 400「简历和 JD 可能填反了」 | 两个输入框放反了；交换后再诊断 |
