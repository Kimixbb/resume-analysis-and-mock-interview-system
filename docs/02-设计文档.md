# 基于多Agent协作的简历诊断与模拟面试系统 — 设计文档

## 1. 设计概述

输入简历文本与目标岗位 JD，系统经「解析 → 匹配诊断、风险拷问(并行处理) → STAR 重写」三步，输出一页诊断报告：匹配分与差距、风险标红与最多五个追问、最差经历的改前/改后对比。

## 2. 总体设计

### 2.1 运行流程

系统四段式流程：一次提交完成解析，匹配与拷问并行执行，两段结果都返回后一次事务落库，再渲染；问答与重写是诊断之后的两个独立动作。前端（Streamlit）与后端（FastAPI）是两个进程，通过本机 HTTP 交换 JSON，以下步骤均由前端按顺序发起。

```text
① 输入校验（前端）
      │ resume_text / jd_text（截断后）
      ▼
② POST /api/parse                              LLM #1
      │ parsed + req
      ├────────────────────────┐
      ▼                        ▼
③ POST /api/match        POST /api/interrogate   LLM #2 / #3（并行）
      │ score + gaps          │ risks + questions + weakest_experience_id
      └───────────┬───────────┘
                  ▼
④ POST /api/report（一次事务）
      │ 写 resume / jd / report，返回 report_id
      ▼
⑤ 前端展示结果（分数 / 差距 / 标红 / 追问）
      │
      ├──► ⑥ POST /api/qa        逐题回答（一次一个）→ 点评 → 更新 report.qa
      ├──► ⑦ POST /api/rewrite   按钮触发 → LLM #4 → 更新 report.rewrite
      └──► ⑧ GET /api/report/{id}  刷新回显（页面加载时）
```

| 步骤 | 触发 | 接口 | 输入 | 输出 | 落库 |
| --- | --- | --- | --- | --- | --- |
| 1 输入校验 | 点击「开始诊断」 | — | 两段文本 | 截断后的文本 | 无 |
| 2 解析 | 自动 | `POST /api/parse` | `resume_text, jd_text` | `parsed, req` | 无 |
| 3 匹配 | 自动、与 4 并行 | `POST /api/match` | `parsed, req` | `score, gaps` | 无 |
| 4 拷问 | 自动、与 3 并行 | `POST /api/interrogate` | `parsed, req` | `risks, questions, weakest_experience_id` | 无 |
| 5 汇总落库 | 3、4 都返回 | `POST /api/report` | 原始文本 + 两段结果 | `report_id` | `resume` / `jd` / `report` |
| 6 展示 | 落库成功 | — | `report_id` | 页面内容 | 无 |
| 7 问答 | 逐题提交回答 | `POST /api/qa` | `report_id, question_index, answer` | `comment` | `report.qa` |
| 8 重写 | 点击按钮 | `POST /api/rewrite` | `report_id` | `before, after, star, improved_score` | `report.rewrite` |
| 9 回显 | 页面加载 | `GET /api/report/{id}` | `report_id` | 聚合报告 | 无 |

`questions` 最多 5 条，按简历实际薄弱点生成，每条指向一条具体风险；风险不足时不凑数，没有致命问题可以为空。

问答阶段**一次只显示一个问题**：用户答完当前题、看到点评后，再进入下一题；问题集合在诊断时已经固定，不会根据回答生成新问题。逐题展示只影响前端，后端仍是单次问答接口。

### 2.2 依赖与并行

```text
parse ──► match ──────┐
  │                    ├──► report ──┬──► rewrite
  └────► interrogate ──┘             └──► qa
```

- **解析是唯一硬依赖**：没有 `parsed`，匹配和拷问都无从开始，因此解析失败直接终止本次诊断。
- **匹配与拷问互不依赖**：两者都只吃 `parsed + req`，可以并发；这是把 3 轮串行压缩成 2 轮的关键。
- **落库依赖两段都完成**：报告在 `POST /api/report` 里一次写入（见决策 2），不采用“谁算完谁写一段”，避免出现只有分数没有风险的半成品。
- **重写与问答依赖 `report_id`**：它们都作用于一份已经存在的报告，所以必须等落库成功后才能用。
- 依赖图无环，也没有反向调用：下游不会反过来调用上游模块。

### 2.3 失败处理

诊断链路中任何一步失败都终止本次诊断，让用户重新开始；问答和重写失败只影响当前动作，重试即可。

- 输入不合法：返回 `400`，前端就地提示，不发起请求。
- 解析 / 匹配 / 拷问失败（超时、非 JSON、字段缺失）：返回 `422`（格式错误）或 `500`（超时、网络异常），前端提示“失败，请重试”，本次诊断结束。
- 汇总落库失败：返回 `500`，事务回滚，不留下半成品。
- 报告不存在：返回 `404`。

| 情况 | 返回 | 前端行为 |
| --- | --- | --- |
| 输入为空 / 过短 / 超长 | `400` | 输入框下方提示，不请求 |
| LLM 输出格式错误 | `422` | 提示“生成失败，请重试” |
| LLM 超时 / 网络异常 | `500` | 提示“服务超时，请重试” |
| 落库失败 | `500` | 提示“保存失败，请重试” |
| 报告不存在 | `404` | 提示“报告不存在，请重新诊断” |

## 4. 模块设计

### 4.1 平台骨架（成员 C）

- `config.py` 加载环境变量，缺关键项启动即失败。
- `llm.py` 统一超时、重试一次、JSON 提取、错误抛出。
- `db.py` / `models.py` 是唯一执行 SQL 的地方。
- 不引入依赖注入层：`llm.py` 提供函数，`db.py` 提供 `get_session()` 上下文管理器；测试用 monkeypatch 替换。
- `main.py` 注册路由、挂异常处理器、启动时建表。
- `errors.py` 定义异常和错误码。

### 4.2 M1 解析（成员 A）

| 项 | 内容 |
| --- | --- |
| 职责 | 把简历和 JD 两段纯文本转成结构化 JSON |
| 输入 | `resume_text`、`jd_text`（已截断） |
| 输出 | `parsed`（ResumeParsed）、`req`（JDReq） |
| 依赖 | 无，链路的起点 |


### 4.3 M2 匹配（成员 B）

| 项 | 内容 |
| --- | --- |
| 职责 | 按目标岗位给简历打分，并给出 3 条关键差距 |
| 输入 | `parsed`、`req` |
| 输出 | `score`、`gaps`（恰好 3 条） |
| 依赖 | M1 的 `parsed` / `req` |

**打分维度**

| 维度 | 权重 | 看什么 |
| --- | --- | --- |
| 硬性技能覆盖度 | 40% | JD 的硬性要求有多少在简历里出现 |
| 项目经历相关性 | 30% | 项目场景、职责、技术栈和岗位是否匹配 |
| 量化成果充分度 | 20% | 有没有数字、基线、结果 |
| 行业/工具匹配 | 10% | 行业背景、常用工具是否对口 |


### 4.4 M3 拷问（成员 C）

| 项 | 内容 |
| --- | --- |
| 职责 | 找出简历里的风险片段，标红并生成最多 5 个致命追问 |
| 输入 | `parsed`（含 `raw_text`）、`req` |
| 输出 | `risks`、`questions`（0–5 条）、`weakest_experience_id` |
| 依赖 | M1 的 `parsed` / `req` |


**规则层**

| 类型 | 判定 | 例子 |
| --- | --- | --- |
| 空话 | 命中词典：认真负责、沟通能力强、团队协作、学习能力强、抗压、责任心强、一致好评 | “认真负责、沟通能力强” |
| 无数字 | 分句含“大幅/显著/明显/极大/全面提升/有效”，且分句里没有数字、百分比、倍数、QPS、ms | “大幅提升了系统性能” |
| 逻辑矛盾 | 日期起止倒置、结束时间晚于当前、教育结束早于工作开始 | “2024.09–2024.06” |

**追问生成规则**

- 先有风险，再有追问：每条追问必须指向 `risks` 里的一条，带 `risk_index`。
- 数量 `N = min(5, 致命风险数)`；有几条出几条，不凑通用题。
- 按致命程度排序：逻辑矛盾 > 无数字 > 空话；与 JD 直接相关的缺口优先。
- 没有致命风险时，`questions` 为空，页面显示“未发现致命问题”。
- 不生成“你最大的缺点是什么”这类与简历无关的题目。


### 4.5 M4 重写与存储（成员 D）

| 项 | 内容 |
| --- | --- |
| 职责 | STAR 重写、报告落库与回显、问答点评、前端页面 |
| 输入 | `report_id`（重写/问答）；报告落库时接收全部上游结果 |
| 输出 | 重写结果、报告详情、问答点评、可运行页面 |
| 依赖 | M1/M2/M3 的契约与样例；平台骨架由 C 提供 |

**4.5.1 STAR 重写**

1. 按 `report_id` 取 `parsed`、`req`、`risks`、原 `score`。
2. 目标经历 = 请求里的 `experience_id`，否则用 `weakest_experience_id`。
3. 用目标经历原文、风险、JD 关键词拼 Prompt，调 LLM。
4. 校验 `before/after/star` 四要素；`improved_score` 若 ≤ 原分，钳制为 `score + 5`（上限 100）。
5. 更新 `report.rewrite`，返回对比结果。

**4.5.2 报告落库与回显**

- `POST /api/report` 一次事务写 `resume`、`jd`、`report` 三张表，返回三个 id。
- 任一步失败整体回滚，不留下半成品。
- `GET /api/report/{id}` 联查三张表，反序列化 JSON 字段，返回前端可直接渲染的结构。

**4.5.3 追问点评**

- `POST /api/qa` 按 `question_index` 从报告里取出原题，不信任前端传的问题文本。
- 规则点评，不调 LLM：没数字 → 缺量化；少于 30 字 → 缺细节；含“大概/可能/应该” → 缺具体事实。
- 追加写入 `report.qa`，一条记录包含题号、问题、回答、点评。

**4.5.4 前端展示**

- 页面形式、布局、控件由前端决定，本文不约束。
- 需要展示：分数、差距、标红、追问、重写对比、问答点评。
- 标红直接用 `render_highlighted(raw_text, risks)` 生成的 HTML。
- 追问一次显示一个，答完显示点评再进入下一题。

## 5. 接口与数据契约

### 5.1 接口总览

| # | 方法 | 路径 | Owner | 用途 | 超时 |
| --- | --- | --- | --- | --- | --- |
| 1 | POST | `/api/parse` | A | 解析简历与 JD | 30s |
| 2 | POST | `/api/match` | B | 匹配打分与差距 | 30s |
| 3 | POST | `/api/interrogate` | C | 风险与追问 | 30s |
| 4 | POST | `/api/report` | D | 汇总落库 | 5s |
| 5 | GET | `/api/report/{report_id}` | D | 报告回显 | 5s |
| 6 | POST | `/api/rewrite` | D | STAR 重写 | 30s |
| 7 | POST | `/api/qa` | D | 逐题点评 | 5s |


### 5.2 `POST /api/parse`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `resume_text` | string | 是 | 简历纯文本，strip 后 100–8000 字，超出截断 |
| `jd_text` | string | 是 | JD 纯文本，strip 后 50–8000 字，超出截断 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `parsed` | ResumeParsed | 结构化简历，`raw_text` 等于请求中的 `resume_text` |
| `req` | JDReq | 结构化岗位要求 |

**错误**：`400` 输入不合法；`422` LLM 输出格式错误；`500` 超时或网络异常。


### 5.3 `POST /api/match`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `parsed` | ResumeParsed | 是 | M1 输出 |
| `req` | JDReq | 是 | M1 输出 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `score` | int | 0–100 |
| `gaps` | Gap[3] | 恰好 3 条差距 |
| `dimensions` | object | 可选，各维度得分，仅前端展示 |

**错误**：`400` 入参不完整；`422` 分数越界或差距不是 3 条；`500` LLM 异常。

### 5.4 `POST /api/interrogate`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `parsed` | ResumeParsed | 是 | 必须包含 `raw_text` 与 `experiences[].raw` |
| `req` | JDReq | 是 | 用于判断风险与岗位的相关性 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `risks` | RiskItem[] | 风险清单，含类型、片段、原因、偏移 |
| `questions` | Question[] | 0–5 条，每条带 `risk_index` |
| `weakest_experience_id` | string | 最差经历 id，必须在 `parsed.experiences` 中存在 |

**错误**：`400` 缺少 `raw_text`；`422` 问题超 5 条、`risk_index` 越界、id 不存在；`500` LLM 异常。

### 5.5 `POST /api/report`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `resume_text` | string | 是 | 截断后的简历原文 |
| `jd_text` | string | 是 | 截断后的 JD 原文 |
| `parsed` | ResumeParsed | 是 | M1 输出 |
| `req` | JDReq | 是 | M1 输出 |
| `score` | int | 是 | M2 输出 |
| `gaps` | Gap[3] | 是 | M2 输出 |
| `risks` | RiskItem[] | 是 | M3 输出 |
| `questions` | Question[] | 是 | M3 输出，可为空数组 |
| `weakest_experience_id` | string | 是 | M3 输出 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `report_id` | int | 报告主键，后续问答/重写都用它 |
| `resume_id` | int | 简历主键 |
| `jd_id` | int | JD 主键 |

**错误**：`400` 嵌套模型不合法；`500` 数据库异常，整体回滚。

**事务**：一次写入 `resume`、`jd`、`report`；任一步失败全部回滚。

### 5.6 `GET /api/report/{report_id}`

**路径参数**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `report_id` | int | 报告主键 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `report_id` | int | 报告 id |
| `resume_text` | string | 简历原文 |
| `parsed` | ResumeParsed | 结构化简历 |
| `jd_text` | string | JD 原文 |
| `req` | JDReq | 结构化岗位要求 |
| `score` | int | 匹配分 |
| `gaps` | Gap[3] | 差距 |
| `risks` | RiskItem[] | 风险 |
| `questions` | Question[] | 追问 |
| `weakest_experience_id` | string | 最差经历 |
| `qa` | QaEntry[]? | 已答记录，可为空 |
| `rewrite` | RewriteResult? | 重写结果，可为空 |
| `created_at` | string | 创建时间 |

**错误**：`404` 报告不存在。

### 5.7 `POST /api/rewrite`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `report_id` | int | 是 | 已落库的报告 |
| `experience_id` | string | 否 | 指定经历；不传则用报告里的 `weakest_experience_id` |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `before` | string | 改写前原文 |
| `after` | string | 改写后文本 |
| `star` | Star | S/T/A/R 四要素 |
| `improved_score` | int | 复评分，保证大于原分 |

**错误**：`400` 经历 id 不存在；`404` 报告不存在；`422` STAR 字段缺失；`500` LLM 异常。

### 5.8 `POST /api/qa`

**请求**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `report_id` | int | 是 | 报告 id |
| `question_index` | int | 是 | 题目下标，从 0 开始，必须在范围内 |
| `answer` | string | 是 | 用户回答，1–1000 字 |

**响应**

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `comment` | string | 一句点评 |

**错误**：`400` 下标越界或回答为空；`404` 报告不存在；`500` 数据库更新失败。

**说明**：后端按 `question_index` 从报告里取原题，不接收前端传来的问题文本；同一题重复提交按覆盖处理。


### 5.9 错误码

| code | HTTP | 含义 | 典型场景 |
| --- | --- | --- | --- |
| `INVALID_INPUT` | 400 | 入参不合法 | 文本过短、回答为空、下标越界 |
| `NOT_FOUND` | 404 | 资源不存在 | 报告 id 查不到 |
| `LLM_OUTPUT_INVALID` | 422 | LLM 输出不符合契约 | JSON 非法、字段缺失、条数越界 |
| `LLM_UPSTREAM_ERROR` | 500 | LLM 超时或网络异常 | 请求超时、连接失败 |
| `DB_ERROR` | 500 | 数据库写入或查询失败 | 落库异常、事务回滚 |

- `GET /api/report/{id}` 联查三张表；JSON 字段反序列化后返回。

## 7. 前端展示要求

页面形式、布局、组件由前端自己决定，本文不约束；只要求把下面这些内容展示出来。

### 7.1 展示内容

| 内容 | 数据来源 |
| --- | --- |
| 匹配分、3 条差距 | `/api/match` |
| 简历原文与风险标红 | `/api/parse` 的 `raw_text` + `/api/interrogate` 的 `risks` |
| 追问列表 | `/api/interrogate` 的 `questions` |
| STAR 改前 / 改后、复评分 | `/api/rewrite` |
| 问答点评 | `/api/qa` 的 `comment` |

### 7.2 操作要求

| 用户操作 | 调用 | 成功后展示 |
| --- | --- | --- |
| 开始诊断 | `/api/parse` → 并行 `/api/match`、`/api/interrogate` → `/api/report` | 上表内容 |
| 生成 STAR 重写 | `/api/rewrite` | 改前/改后、复评分 |
| 提交当前题回答 | `/api/qa` | 点评与「下一题」 |
| 下一题 | 无请求 | 下一题 |
| 刷新页面 | `/api/report/{id}` | 恢复页面 |

### 7.3 刷新恢复

- 刷新后应能恢复本次报告；建议把 `report_id` 放进 URL，加载时调 `GET /api/report/{id}`。
- 状态存在哪、怎么存，由前端定。
- 未提交的输入刷新后丢失，首版接受。

### 7.4 追问交互

- 一次只展示当前题；提交后展示点评，再进入下一题。
- 题号、进度、输入控件、提示样式由前端定。
- 最后一题答完，展示全部问答与点评。
- `n = 0` 时显示“未发现致命问题”。
- 首版不支持跳题、不支持回头改答案。

### 7.5 失败提示

| 场景 | 提示 | 后续 |
| --- | --- | --- |
| 输入为空 / 过短 | 提示用户修正 | 修正后重试 |
| `422` | “生成失败，请重试” | 重新发起诊断 |
| `500` | “服务超时 / 保存失败，请重试” | 重新发起 |
| `404` | “报告不存在，请重新诊断” | 清空 `report_id`，回到输入 |

## 9.总结与提示

### 9.1 目录与文件（文件名: 作用）

```text
backend/                          : 后端总目录，启动时从这里进
backend/app/                      : 后端代码包，入口是 main.py
backend/app/main.py               : FastAPI 入口：创建应用、注册路由、挂异常处理器
backend/app/core/                 : 公共设施（配置、数据库、LLM、异常），不写业务
backend/app/core/__init__.py      : 标记 core 是 Python 包(可以空着)
backend/app/core/config.py        : 读 .env：API Key、模型名、数据库地址
backend/app/core/db.py            : 数据库连接、Session、增删改查
backend/app/core/models.py        : 三张表的 ORM 定义
backend/app/core/llm.py           : 调 LLM：超时、重试、JSON 解析与校验
backend/app/core/errors.py        : 自定义异常和错误码
backend/app/contracts/            : 接口请求/响应模型（Pydantic）
backend/app/prompts/              : Prompt 模板
backend/app/services/             : 业务逻辑：解析、打分、拷问、重写
backend/app/routers/              : 接口入口：路径、参数、返回
backend/fixtures/                 : 样例数据（简历、JD、各模块真实输出）
backend/scripts/                  : 工具脚本(比如建立数据库)
backend/tests/                    : 测试代码
backend/data/                     : SQLite 文件，运行时生成，不提交(连接数据库的时候这里会生成文件)
frontend/                         : 前端页面（Streamlit）
docs/                             : 设计文档、需求文档等等
```

### 9.2 注意点

1. 异常：service 做相应的的异常处理，有问题就 `raise`错误，异常类放 `core/errors.py`，统一由 `main.py` 转成 `{code, message}`。这部分由 C 维护。
2. contracts：放接口的请求/响应模型和跨模块共享结构（DTO），只写字段、不写业务。跨接口、跨模块、嵌套结构才建类；数据库表在 `core/models.py`，不要混进来。
3. 数据流：每个模块只关心自己的输入输出。后端模块之间是函数直接调用传参；前端通过接口拿数据。
4. router要少: 只调用后端服务，给出接口url
